# Проверенный живой мост Antigravity

11 ноября 2026: проведён реальный цикл через уже запущенную беседу `/tg`, без Antigravity CLI и управления экраном.

## Что проверено

- Однократная команда `CMD-071` передана существующему CRM-ожидателю через его `QueueService`.
- Беседа Antigravity закрыла эту команду локально и запустила новый ожидатель Viewer.
- `T-000001`: Antigravity выполнил Node/git и вернул точный одноразовый challenge; Codex проверил отчёт и одобрил.
- После первого отчёта беседа снова запустила ожидатель и получила `T-000002` с другим challenge.
- Второй отчёт также проверен и одобрен. После него подтверждён живой `runtime/cli/wait-task.ts` для проекта `viewer`.
- Отчёты не запрашивали Telegram-уведомления или TTS. Никакая модель не вызывалась координатором для выполнения этих диагностик.

Подробности: [live-bridge-evidence.json](live-bridge-evidence.json). Модель исполнителя мост не проверял; поле model не было заявлено исполнителем.

## Текущее подключение

Рабочий каталог — `outputs/Viewer2` этой разработки. Общая для координатора и исполнителя база — `.viewer-live/agent-queue.db` в этом каталоге. Это отличается от домашней базы по умолчанию: всегда передавайте `--db` или `VIEWER_QUEUE_DB`.

```powershell
npm run --silent agents:task -- submit '@spec.json' --db='.viewer-live/agent-queue.db'
npm run --silent agents:task -- wait T-000003 --timeout-sec=60 --db='.viewer-live/agent-queue.db'
npm run --silent agents:task -- verdict T-000003 approve --by=codex --db='.viewer-live/agent-queue.db'
```

Исполнитель в выделенной беседе:

```powershell
npm run --silent agents:wait -- --project=viewer --executor=antigravity --db='.viewer-live/agent-queue.db'
```

Ожидатель должен быть запущен самой беседой как ожидающая инструментальная задача. Запуск его координатором в отдельной консоли не подключает модель.

## Совместимость со старым Dev Bot

`runtime/bridge/devbot.ts` — адаптер однократной передачи управления: `enqueue`, `get`, `complete-local`. Он использует существующий QueueService, проверяет канонический projectId и не вызывает Telegram/TTS. Повторная постановка с тем же ключом не создаёт второй bootstrap.

Старая JSON-очередь остаётся нетранзакционной: адаптер не предназначен для постоянной параллельной записи. Исходники Dev Bot не изменялись. Беседа, участвовавшая в проверке, теперь слушает очередь Viewer, а не старую CRM-очередь. Автоматическая доставка телефонных команд старого бота в новую очередь ещё не реализована. Для возврата к старому режиму нужно остановить новый ожидатель в этой беседе и снова выполнить `/tg`; глобальные процессы бот-шлюза этим тестом не переключались.

## Почему зависали тесты

Шесть процессов ждали появления файла `go`; родитель делал `rename(go.tmp, go)`. В Windows sandbox это завершалось EPERM. Тест падал, но процессы оставались ждать файл, удерживая Node test runner.

Файловый сигнал заменён IPC-сообщением с общим временем старта. Добавлены тайм-аут READY, обработка раннего выхода, остановка всех workers в finally и при отмене теста. Отдельный тест проверяет сбой запуска worker. Полный прогон: 54 passed, 0 failed; TypeScript — без ошибок.
