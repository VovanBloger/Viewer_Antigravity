# Isolated project environments

`EnvironmentManager` stores allocations in its own SQLite WAL database under an explicit workspace root. Register opaque bot IDs with their fixed Telegram network; pass an exact registered-project resolver from the shared queue. `allocate` reserves a unique bot, local port, branch, worktree path, data directory and application DB. Repeated allocation of the same environment is idempotent; a second branch cannot share these resources. A multiplayer scenario uses one environment with several actor IDs. There is no game-specific code.

`createWorktree` emits `git worktree add -b <branch> <owned-path> HEAD` through an injected executable/argv runner. It never merges, pushes, deploys or removes a worktree. The caller executes this command only in an authorized project repository. Existing directories and symlink escapes are rejected. Bot tokens are deliberately absent from the environment schema; local adapters resolve opaque bot IDs separately.

`start` uses an injected `ProcessFactory`, supplies the isolated port/data/database paths, and waits for a localhost HTTP readiness URL on the allocated port. Status transitions are persisted; only the owning manager can stop a live process. Start failure stops its exact child handle and persists a redacted error. Allocations are retained after stop so restart does not silently change a bot or database. A manager reopened after a crash conservatively reports `EXTERNAL_PROCESS_OWNER` for a previously ready/starting environment; external process recovery requires explicit reconciliation. It does not kill stored PIDs or arbitrary host processes.

`localProcessFactory` spawns only explicitly allowlisted absolute executable paths with argv, `shell:false`, and hidden Windows windows. Children receive a small OS environment plus their isolated port/data/database paths, without inheriting model API credentials. Local readiness has a deadline and rejects redirects. Stop uses only the child handle created by that factory. `gitWorktreeRunner` accepts only the worktree-add operation. These are for trusted local project manifests, not commands received from an untrusted webpage.

The tests cover allocation persistence/conflicts, injected lifecycle errors and an actual local Node HTTP child with readiness/stop and credential-environment isolation. Bot provisioning, attaching browser actors and GameTycone integration are not yet wired into the UI. These checks are not live Telegram acceptance. A stopped environment retains its resources; explicit resource release and crash reconciliation remain operator tasks.
